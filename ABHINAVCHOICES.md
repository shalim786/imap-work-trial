## Final behavior and design rationale

- Inbox membership means `received` and not `trash`. Other protected-label visibility depends on credential permission and the explicit full-visibility assertion.
- AgentMail is the source of read state; absence of `unread` maps to `\Seen`. Writable read/unread changes update AgentMail labels. `starred` maps to `\Flagged` for display; unsupported flag or mailbox writes must return a tagged failure.
- Raw RFC message bytes are preserved. Literal lengths and RFC822 sizes count bytes, including encoded Unicode. BODY.PEEK does not set Seen; a normal body read does.
- Paginated list calls exhaust pages and detect malformed/cyclic pagination rather than silently truncating. Events assist diagnosis and refresh; they are not an assumed deletion log.
- SQLite/PostgreSQL persist identities and revisions. Reconciliation retires confirmed removals; reappearance receives a new UID. Existing active UIDs survive reconnects and process restarts. Session sequence numbers are view-dependent and may change after EXPUNGE.
- Command parsing, literal limits, retry policy, write timeouts, disconnect cancellation, safe errors, and cache budgets prevent malformed input or upstream failure from exposing keys or hanging abandoned sessions. FETCH retries are intentionally persistent while the client remains connected.
- Metadata groups are larger than raw preparation groups. Fresh authorization remains necessary; caching raw content does not cache access permission. Raw TTL is measured from completion and the cache is bounded and credential-isolated.
- AWS shares UID state, reconciliation locks, and credential rate budgets through PostgreSQL. Raw caches remain instance-local and disposable. Shared metadata snapshots are scoped by credential and short-lived; fresh authentication precedes access.
- AWS uses public TLS at the NLB, private instance traffic, and verified RDS TLS. Health requires a ready database. Fresh hosted initialization is automated and validated; migration remains explicit, and shutdown marks workers unready before bounded session draining.
- Sending is a dedicated authorized testcase script, not SMTP support in the IMAP bridge. Draft upload, APPEND, arbitrary mailbox mutation, and complete production-client compatibility are not implied by basic read support.

## Reliability tradeoffs and unresolved issues

| Choice | Why it was made | Cost, issue, or next validation |
| --- | --- | --- |
| Two or more active application instances, one shared PostgreSQL writer | Any healthy instance can serve a new IMAP connection with the same durable identities. There is no designated application leader or follower. | RDS Multi-AZ has a primary and standby, rather than independent application writers. Database failover can interrupt operations. Hosted reconnect/failover evidence is still required. |
| One renewable reconciliation lease per namespace/inbox | Prevent conflicting membership commits and stale workers writing after takeover; API calls hold no pooled database connection. | Refreshes and read-state mutations for the same inbox serialize. A large slow inbox is a hotspot. An abandoned acquisition can leave a lease until its 30-second expiry. |
| Transactional fencing and revisions | A worker that loses ownership cannot publish stale mappings or invalidate another worker's snapshot. | AgentMail and PostgreSQL cannot participate in one atomic transaction. A crash during STORE can leave an ambiguous remote change; the next complete scan resolves it. |
| PostgreSQL request pacing shared across workers | Adding instances does not multiply the API request rate allowed for one credential. | Coordination adds database round trips. More instances cannot remove a credential's upstream rate limit; API concurrency is still bounded separately in each process. |
| Full paginated refresh and targeted missing-ID reads | New mail and confirmed removals converge without assuming the event API is a complete deletion feed. | Refresh cost grows with inbox size and removals. API pages are not a transactional snapshot, so changes during pagination may only converge on a later refresh. Events remain one diagnostic page, not a persisted incremental cursor. |
| Explicit full-visibility assertion | A missing message's 404 can support retirement only when the operator asserts that permissions do not hide messages. | A permission-limited key or incorrect assertion can make disappearance ambiguous. The safe default retains the prior view when a removal cannot be confirmed. Credentials sharing one inbox are assumed to represent a compatible visibility model. |
| Per-instance credential-scoped raw cache | Reduce repeated body/attachment downloads while bounding temporary storage and preserving raw bytes. | Cache contents are disposable and not shared between instances; reconnecting to another worker can require downloads again. Fresh authorization/metadata checks still make API calls. The 120-second TTL is not a persistent email archive. |
| Persistent transient FETCH retries | Honor the requested eventual-success behavior while emitting complete ordered prefixes. | A connected client may wait indefinitely through an outage and occupy a slot. Disconnect cancellation, rate limits, write timeouts, and connection caps bound abandoned work, but they do not promise a finite successful FETCH duration. |
| Bounded raw staging and parser limits | Keep large bodies, malformed requests, and slow readers from consuming unlimited resources. | Limits deliberately reject valid requests outside this slice. SEARCH involving raw content has batch/byte limits. Large metadata lists and per-session views still consume memory; measured RSS is not a proof of a maximum-memory bound. |
| CPU autoscaling with configurable EC2 instance and connection caps | Provide an understandable first scaling policy without new telemetry infrastructure. | Idle IMAP connections can fill slots while CPU stays low. A custom active-connection utilization metric is not yet implemented. Existing TCP sessions do not migrate when instances scale out. Scale-in can disconnect clients after the drain deadline. |
| Pool of up to 12 database connections per instance | Bound each task's database resources. | Total potential connections grow with task count: eight instances can request 96 pool connections, plus separate initialization/operator work. Check RDS connection and memory capacity before raising limits. |
| Database-based readiness | Avoid routing clients to a worker that cannot validate durable identity storage. | Readiness does not prove AgentMail is healthy or credentials are valid. Monitor upstream failures separately; removing every task during a shared upstream outage would not repair the upstream. |
| Private TCP after NLB TLS termination | Follow the chosen AWS architecture while terminating public TLS with ACM. | Public traffic and RDS use TLS, but the NLB-to-task leg is plaintext in the private network. End-to-end application TLS would be an additional architecture choice. |
| Separate local and AWS source copies | User explicitly preferred redundant folders for ease of reasoning and independent setup. | Fixes can drift. Every shared behavior change needs deliberate application to both copies and separate test runs. |
| Simple retained credential-policy registries | Reuse pacing state across connections within a process. | In-memory policy entries and persistent request-budget rows have no general credential-retention eviction policy yet. Arbitrary invalid login keys can grow the process registry over time. |
| One database role for setup and runtime | Keeps the exercise's initialization and deployment sequence straightforward. | Runtime currently uses the database owner credentials. Separating schema migration privileges from a least-privilege runtime role is further hardening, not a completed feature. |

The code is a tested vertical slice with prepared AWS infrastructure. It is not a claim of a partition-tolerant, independently writable distributed mailbox service, complete IMAP compatibility, or production capacity. SMTP, APPEND/drafts, arbitrary folder writes, IDLE, QRESYNC/CONDSTORE, and client compatibility beyond the exercised commands remain outside the implemented slice. TLS and AWS preparation were later additions to the original exercise scope.

## Current AWS architecture — authoritative, supersedes historical trial controls

The assigned stack remains **agentmail-org/imap-template/intern**, with IMAP at **trial-imap.imap.to**. The existing imap.to website resources are preserved. Pulumi drives the image build, upload, database provisioning, instance bootstrap and scaling configuration. No AWS deployment has been performed by this work.

The current deployment uses **EC2 Auto Scaling**, default **two to eight t3.small instances**, with a CPU target-tracking policy. The instances are peers sharing PostgreSQL; neither is a master for IMAP. The database has a primary and Multi-AZ standby for failover. Each EC2 host runs one Docker container, supervised by systemd. Docker packages Python and its dependencies consistently; Pulumi invokes the build automatically. There is no Fargate service and no ECR repository.

The immutable Docker image archive is stored in a private encrypted S3 bucket. Pulumi's secret databasePassword is used for RDS and a private encrypted S3 runtime configuration object. Instances can read only the application and configuration object through their instance role. The password is absent from user data, downloaded to a root-owned mode-0600 file, and passed to Docker through an environment file. AWS-managed S3 encryption protects storage, while IAM governs access; authorized bucket readers can obtain the configuration. This is deliberately simpler than Secrets Manager and has no automatic password rotation.

The NLB terminates public TLS on 993 using ACM and forwards private TCP to 1143. Readiness checks use 8080. App subnets use NAT for outbound AgentMail HTTPS; database subnets have no internet route. PostgreSQL requires verified TLS and holds UID identities, mailbox leases/snapshots and shared API pacing. Each container's bounded raw cache remains disposable. Hosted mappings start fresh; local SQLite and AgentMail messages are not imported or deleted.

**Removed controls:** no automatic expiry, $200 budget, cleanup Lambda, EventBridge schedule, SNS, SQS, Secrets Manager, CloudWatch agent, explicit operational alarms or memory scaling policy. Standard EC2 metrics used by CPU target tracking still exist. Docker logs are locally bounded; operators use instance/systemd/container diagnostics. There is no promise of automatic teardown or a spending ceiling. Charges continue until manual removal.

Manual teardown disables the IMAP module through Pulumi configuration, reviews the resulting preview, and applies it while preserving website resources. Never run pulumi destroy on the shared assigned stack. Database protection must be deliberately handled before deletion, and a backup/UID-history decision is required. Existing connections can be interrupted by rolling replacement, unhealthy-instance termination or scale-in; CPU alone cannot measure idle connection pressure.

### Application packaging and initialization function reference

- **packageApplication**, [package-application.ts](/Users/work/Desktop/imap-work-trial/aws/infra/package-application.ts): walk the allowlisted Dockerfile, Python package, pinned dependency lock, initialization script and public CA bundle; hash source paths/bytes; build a Linux amd64 image; export and gzip its Docker archive; return immutable archive SHA256, S3 key and image tag. Generated output is local and ignored. Private environment/state files never enter the allowlisted build context. Build failure stops deployment.
- **packageApplication.visit**, same file: recursively visit sorted entries, skip Python bytecode caches, reject symlinks and collect regular allowlisted files. Sorting makes source identity deterministic. External dependency availability and the Docker toolchain remain prerequisites.
- **buildUserData**, [ec2-bootstrap.ts](/Users/work/Desktop/imap-work-trial/aws/infra/ec2-bootstrap.ts): shell-quote resolved identifiers, validate archive hash and image tag, install Docker/AWS CLI, download and verify the S3 archive, load the image, securely download runtime configuration, and install/start the systemd service. Startup initializes the schema before launching IMAP. systemd retries failures; NLB readiness gates useful traffic. Ubuntu repositories and AWS CLI downloads are startup dependencies.
- **buildUserData.q**, same file: quote shell values safely so generated bucket/object identifiers cannot become shell code.
- **ensure_database**, [ensure_database.py](/Users/work/Desktop/imap-work-trial/aws/scripts/ensure_database.py): take a PostgreSQL advisory initialization lock shared across concurrent boots; create the schema/generation only when empty; validate exact expected tables and required columns; invoke normal store validation; release the lock. Existing or partial schemas are never cleared or silently repaired. Startup fails closed if validation fails.
- **ensure_database.main**, same file: load environment/configuration, require PostgreSQL, invoke initialization and return a sanitized success/failure exit status without exposing the DSN or password.
- **aws/infra/index.ts module evaluation**: retain existing website outputs and conditionally load the IMAP module. Disabling that module creates a reviewable Pulumi removal plan rather than destroying the shared stack.
- **aws/infra/website.ts module evaluation**: preserve the independent S3/CloudFront website and DNS/certificate resource identities.
- **aws/infra/imap.ts module evaluation**: resolve configuration/provider outputs and create the resources above; transform secret output into the private S3 runtime object; generate bootstrap script and EC2 launch revisions; attach CPU scaling when enabled. The runtime-object revision participates in user data so configuration changes can trigger rolling refresh.
